# Dynamoose Changelog

---

### 🚨 Breaking Changes 🚨

- `Item.save` now applies custom type conversion to the item it resolves with, so custom typed attributes (such as `Date`) are returned in the same representation as `Model.get`. Previously `save` resolved with the underlying DynamoDB representation (for example a `number` for `Date` attributes) while `get` resolved with the custom type (a `Date` instance)
- `Model.update` and `Model.transaction.update` now set `createdAt` timestamps with `SET createdAt = if_not_exists(createdAt, :now)`, so an update that creates the item stores `createdAt` with the same value as `updatedAt`, and an update to an existing item keeps its `createdAt`. Previously an update never wrote `createdAt`. An existing item that has no `createdAt` gets the time of its next update, the request built with `return: "request"` has one more attribute name and value for each `createdAt` attribute, and `returnValues: "UPDATED_NEW"` or `"UPDATED_OLD"` now include `createdAt`. A `createdAt` or `updatedAt` attribute that is part of the table key is not set, and a `Combine` attribute that uses `createdAt` throws unless the update sets `createdAt` itself

### Features

- `Model.batchGet` now sends more than 100 keys, and `Model.batchPut` and `Model.batchDelete` more than 25 items, as several DynamoDB requests one after another, and combine their results and unprocessed keys or items. Before, DynamoDB rejected such a batch with `ValidationException: Too many items requested`. A batch sent as more than one request throws an `InvalidParameter` error, before sending any of it, when two of its keys or items have the same key, as DynamoDB does for a single request
- Added a `retryUnprocessed` setting to `Model.batchGet`, `Model.batchPut` and `Model.batchDelete`. With `{"attempts": n}`, Dynamoose sends the keys or items DynamoDB returns as unprocessed again, up to `n` times with exponential backoff and full jitter (`delay`, default 100 ms), and returns only what is still unprocessed after that. Each wait is at most 20 seconds
- Added a `concurrency` setting to `Model.batchGet`, `Model.batchPut` and `Model.batchDelete`, which sends that many of a large batch's DynamoDB requests at a time (default 1)
- Added support for enabling and configuring DynamoDB Streams through Table options
- Added `clientRequestToken` and `retry` settings to `dynamoose.transaction`. `clientRequestToken` is sent as the `ClientRequestToken` of a write transaction, so DynamoDB applies the same transaction only once for 10 minutes. `retry: {attempts, delay}` sends the transaction again, with exponential backoff and full jitter, when DynamoDB cancels it for a `TransactionConflict` or reports `TransactionInProgressException`; any other error is thrown at once. Every attempt sends the same `ClientRequestToken` (the one passed in, or one Dynamoose makes for the call and replaces after a cancellation), so a transaction still in progress is never applied twice, and each wait is at most 20 seconds
- Added a `merge` setting to `Model.update`. Passing `{"merge": true}` updates a nested object in place by writing each provided property to its own document path (`SET attr.sub = :v`), matching how a nested attribute update is expressed against DynamoDB directly, instead of replacing the whole attribute as a map. The default behavior is unchanged
- `condition.not()` now works with `in`, `between` and `beginsWith`, sent as `NOT (a IN (...))`, `NOT (a BETWEEN x AND y)` and `NOT begins_with (a, x)`. Before, these threw `can not follow not()`
- Added support for enabling table deletion protection through the `deletionProtection` Table option. It is applied on create, and on update it can only be turned on; turning it back off requires `update` to explicitly include `deletionProtection`
- Added `Model.itemFromDynamo(attributes)`, which converts an item in DynamoDB's format (such as a DynamoDB Stream `NewImage` or an AWS SDK `Item`) into an item of the model, as `Model.get` would return it, with custom types such as `Date` converted by their `storage` setting. It takes the image typed as `@types/aws-lambda` types it, and decodes the base64 binary values a Lambda event has
- Added support for enabling point-in-time recovery through the `pointInTimeRecovery` Table option, including configuring the recovery window with `pointInTimeRecovery.recoveryPeriodInDays`. As with deletion protection, `update: true` can only turn recovery on; turning it back off requires `update` to explicitly include `pointInTimeRecovery`
- Added a `returnValuesOnConditionCheckFailure` setting to `Model.update`, `Model.create`, `item.save` and `Model.delete`, and so to their `Model.transaction` requests. With `ALL_OLD`, a failed condition (or an existing item for `create`) throws `ConditionalCheckFailedException` with a `conditionCheckFailureItem` property holding the stored item as `Model.get` would return it, so a caller can retry without reading the item again
- Added a `returnItems` setting to `dynamoose.transaction`, so a write transaction resolves with the written items in the same order as the request: a `create` gives the stored item built from the request, an `update` gives the stored item read back in one `transactGetItems` call, and a `delete` or `condition` gives `undefined`. Each item uses the model that built its request and looks as `Model.get` would return it. If the write succeeds but the items can't be returned, the promise rejects with a `TransactionReadError` whose `committed` property is `true`
- Added a `returnValuesOnConditionCheckFailure` setting to `dynamoose.transaction`. Set to `ALL_OLD`, it is passed as `ReturnValuesOnConditionCheckFailure` on every write request that has a condition, and when a condition fails, the `TransactionCanceledException` gets a `conditionCheckFailureItems` property: one entry per request, holding the stored item (as `Model.get` would return it) of each request whose condition failed on an existing item

### Performance

- Improved performance of converting items returned from `scan` and `query` (~2x faster on large result sets). `Schema` now memoizes `attributes`, `getAttributeValue`, `getAttributeType`, and `getAttributeTypeDetails` per schema, and object flattening no longer re-walks each nested value's subtree to detect circular references
- Improved performance of `Model.update` on items with many nested attributes when the schema has nested `required` attributes (~460x faster for a 2,000 element list: 24.6 s to 54 ms). The update flattened the whole item once for every attribute it checked; it now flattens it once
- Improved performance of items containing a long list of attributes with multiple possible types (~4x faster for a 800 element list). Building the type paths for such an item no longer copies the accumulated result once per element

### Bug Fixes

- `@kennethwkz/dynamoose` now depends on `@kennethwkz/js-object-utilities` (installed under the name `js-object-utilities`), a fork whose `entries` treats binary values as leaves and detects cycles in linear time. This fixes `Model.get`, `query` and `scan` throwing `RangeError: Maximum call stack size exceeded` for an item with a large binary attribute (dynamoose/dynamoose#1608). Paths through `__proto__` are ignored by `delete`, as in js-object-utilities 2.2.2
- Fixed `Model.create` and `item.save` resolving with an item that left out the attributes the schema's `saveUnknown` setting allows (for example everything under `order.**`), and `item.save` removing them from the item it was called on. The stored item was correct, and `Model.get` returned them; the returned item now matches it
- Fixed `Model.update` failing with `ValidationException: Two document paths overlap` when the update sets or removes a timestamp attribute itself (for example `{"updatedAt": date}` or `{"$REMOVE": ["updatedAt"]}`). Dynamoose no longer adds its own value for a timestamp attribute that the update already names
- Fixed `deep_copy` dropping sibling properties that share the same object reference (e.g. a single `Date` used for both `createdAt` and `updatedAt`, or a single address used for both `billingAddress` and `shippingAddress`). Circular reference detection now tracks only the current ancestor path rather than every object ever visited, which also removes an infinite-recursion risk on self-referencing arrays and a shared-reference leak on class instances containing circular properties
- Fixed `query.consistent()`, `scan.consistent()`, `query.count()` and `scan.count()` ignoring their argument and flipping the setting on every call, so `consistent(false)` sent `ConsistentRead: true` and calling a method twice turned the setting off. They now take an optional boolean, and calling them without one turns the setting on
- Fixed `Model.update` corrupting arrays, Sets, and Buffers nested inside a map attribute. These values were traversed as if they were nested maps, which produced document paths keyed by array indices or byte offsets, and silently dropped Sets from the update entirely
- Fixed `Item.attributesWithSchema` throwing `node.forEach is not a function` when an object was supplied for an attribute the schema defines as an array
- Fixed `Model.update` rejecting partially specified nested attributes at the type level. Update bodies are now typed as `DeepPartial<T>`
- Fixed the TypeScript type of `table.create({"return": "request"})`, which resolved to `Promise<void>` instead of `Promise<CreateTableInput>` because a general overload came first, and `table.create({})`, which matched no overload because `return` was a required setting
- Fixed the `save` callback being invoked a second time when the supplied callback itself threw an error
- Fixed the `expires` TTL attribute being silently dropped from every model registered against a table after the first. A model attaching to an already-constructed table did not receive the TTL attribute injection the `Table` constructor performs, so its writes stored no TTL attribute at all while DynamoDB continued to report `TimeToLiveStatus: ENABLED`. Affected every table shared by two or more distinct `Schema` objects, across `create`, `transaction.create`, and `update`
- Fixed a global secondary index whose name is unchanged but whose key schema or projection changed being deleted without being recreated. Such an index was only restored on a later `initialize`, leaving the table without it in between. The delete and the recreate are now emitted in the same reconciliation pass, in that order
- Fixed `queriedCount` always being `undefined` on `Model.query` results. The count of items DynamoDB read before applying filters was looked up on the response as `QueriedCount`, a property the DynamoDB API never returns; the `Query` operation reports it as `ScannedCount`, the same as `Scan`. This affected `query.exec`, `query.all`, and `query.count`, in both the array and `count()` response shapes
- Fixed `dynamoose.transaction` get results skipping schema `get` modifiers. Items returned from a `transactGetItems` transaction now run attribute `get` functions the same as `Model.get`, `Model.batchGet`, `Model.query`, and `Model.scan`
- Fixed `Model.update` resolving with an item that skipped schema `get` modifiers. The item returned from the `updateItem` response now runs attribute `get` functions the same as `Model.get`, `Model.batchGet`, `Model.query`, and `Model.scan`
- Fixed `Model.batchGet`, `Model.update` and `dynamoose.transaction` get results not applying the schema `map`/`alias` settings. Items returned from these methods now use the mapped attribute names, the same as `Model.get`, `Model.query`, and `Model.scan`
- Fixed a mapped (`map`/`alias`) attribute being dropped from a returned item when its value was falsy (`0`, `false` or an empty string)
- Fixed `Model.batchGet` throwing `TypeError: Cannot read properties of undefined` when DynamoDB returned an expired item on a table with `expires.items.returnExpired` set to `false`. Expired items are now left out of the result, the same as `Model.query` and `Model.scan`
- Fixed `Model.batchGet` silently leaving out items whose key attribute has a `get` function. Requested keys were matched against the item after its `get` functions ran, so a key stored as `user#1` and returned as `1` never matched; keys are now matched against the item as DynamoDB returned it
- Fixed `Model.batchGet` silently leaving out items, and unprocessed keys, whose key is a `Buffer`. Key values were compared with `===`, which is never true for two `Buffer` instances; they are now compared by content
- Fixed `Date` and `Buffer` key values in `Model.get`, `Model.batchGet`, `Model.delete`, `Model.batchDelete`, `Model.update` and the `Model.transaction` methods. A `Date` or `Buffer` passed as the hash key sent an empty `Key` to DynamoDB, and a `Date` inside a key object threw `Unsupported type passed`. `Date` key values are now converted using the attribute's `storage` setting before the attribute's `set` function runs, the same as when saving an item (previously a key's `set` function received the `Date` itself), and the key types accept `Date` and `Buffer` values. `Model.batchDelete` also now reports unprocessed items whose key is a `Buffer`; key values were compared with `===`, which is never true for two `Buffer` instances
- Fixed a serializer `exclude` path into a nested object or list (such as `"address.city"` or `"lines.0.cost"`) deleting the value from the item itself, so a later `save` could write the change to DynamoDB. The plain objects and lists along each excluded path are now copied before deleting, so the item is left as it was and the serialized output is unchanged. An `exclude` path through an inherited `__proto__`, `constructor` or `prototype` property is now ignored, instead of deleting from a built-in prototype such as `Object.prototype`
- Fixed `condition.not()` before `condition.parenthesis()` or `condition.group()` being silently ignored, so the group was applied un-negated and returned the opposite items. It is now sent as `NOT (...)`
- Fixed a `Date` value in a condition throwing `Unsupported type passed` in `query`, `scan` and conditional writes. A `Date` is now sent the way its attribute stores it (milliseconds, seconds or ISO string), including in `between` and `in` and on nested attributes (`meta.when`), and a `Date` for an attribute that isn't a `Date` throws a clear `InvalidParameter` error
- Fixed `dynamoose.transaction` rejecting with `No value defined: {}` when a `Get` asked for an item that does not exist. The result now has `undefined` at that position, in the same order as the request
- Fixed a raw condition object being silently ignored when its expression property didn't match the request. A `FilterExpression` raw condition passed to `Model.update`, `Model.delete`, `Item.save` or a transaction was dropped, so the write ran without its condition; a `ConditionExpression` raw condition passed to `query` or `scan` was dropped, so no filter was applied. Either property is now used for both, and any other property (such as `ComparisonExpression`, which the documentation previously named) throws an `InvalidParameter` error
- Fixed `Model.update` adding its update expression, names and values to the raw condition object passed in, which made a reused raw condition throw or be ignored on the next request
- Fixed a raw condition object without `ExpressionAttributeValues` (for an expression that uses no values, such as `attribute_exists(#id)`) throwing `The type: #id is invalid`. It is now used as a raw condition, and the request leaves out `ExpressionAttributeValues` unless something else in the request adds values
- Fixed `Model.query` with a raw condition object throwing `Index can't be found for query.`. Dynamoose now splits the raw expression at its top-level `AND`s, picks the index from the parts that are key conditions, and sends those as the `KeyConditionExpression`, leaving the rest in the `FilterExpression`. A second condition on the same key attribute throws an `InvalidParameter` error, because DynamoDB rejects a key attribute in the `FilterExpression`
- Fixed `Model.update` replacing a raw condition's names and values when they used the same placeholders as the update (`#a0`, `:v0`), which made the condition silently check a different attribute or value. The update's placeholders now start after the raw condition's
- Fixed a raw condition object with an empty `ExpressionAttributeNames` (an expression that names its attributes directly, such as `id = :id`) or an empty `ExpressionAttributeValues` sending that empty map, which DynamoDB rejects. An empty map is now left out
- Fixed a raw condition object passed to `condition.parenthesis()` or `condition.group()` being dropped, which made `Model.query` throw `TypeError: Cannot read properties of undefined (reading '0')` and a scan or conditional write run without it. It is now sent in parentheses with its own names and values, and two raw conditions that use one placeholder for different names or values throw an `InvalidParameter` error
- Fixed the `Condition` documentation naming `ComparisonExpression` instead of `ConditionExpression` for raw condition objects, and a raw example using a number instead of a string for an `N` value

### Other

- Fixed intermittent CI failures in timing-based tests. Timestamp tests now check that the value falls between the time before and after the call instead of within 10ms of a single reading, and the `Scan`/`Query` `all` delay and `Table` TTL wait tests allow for timers firing about 1ms early
- Fixed the `Table` constructor's `models` parameter type, which accepted any `Model`. It is now typed as the models `dynamoose.model` returns, so passing a value the constructor rejects at runtime (such as `User.Model`) is a type error instead of a runtime error
