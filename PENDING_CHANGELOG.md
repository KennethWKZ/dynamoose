# Dynamoose Changelog

---

### Maintenance

- Store CLA signatures on a dedicated branch so protected main does not block contributors from signing

### 🚨 Breaking Changes 🚨

- `Model.update` and `Model.transaction.update` now throw an `InvalidParameter` error, before sending, for an update with nothing to write, such as an empty update object or one whose attributes are all skipped. Before, it was sent and DynamoDB rejected the empty update expression with a `ValidationException`. With `{"return": "request"}` and a callback, the error is passed to the callback
- `Item.save` now applies custom type conversion to the item it resolves with, so custom typed attributes (such as `Date`) are returned in the same representation as `Model.get`. Previously `save` resolved with the underlying DynamoDB representation (for example a `number` for `Date` attributes) while `get` resolved with the custom type (a `Date` instance)
- `Model.update` and `Model.transaction.update` now set `createdAt` timestamps with `SET createdAt = if_not_exists(createdAt, :now)`, so an update that creates the item stores `createdAt` with the same value as `updatedAt`, and an update to an existing item keeps its `createdAt`. Previously an update never wrote `createdAt`. An existing item that has no `createdAt` gets the time of its next update, the request built with `return: "request"` has one more attribute name and value for each `createdAt` attribute, and `returnValues: "UPDATED_NEW"` or `"UPDATED_OLD"` now include `createdAt`. A `createdAt` or `updatedAt` attribute that is part of the table key is not set, and a `Combine` attribute that uses `createdAt` throws unless the update sets `createdAt` itself. Set the new `createdAtOnUpdate` schema setting to `false` to keep the old behaviour.
- `new dynamoose.Schema` now throws `The updatedAt timestamp attribute "updatedAt" must not be a hashKey or rangeKey.` when an `updatedAt` timestamp is the schema's `hashKey` or `rangeKey`. Its value changes on every save, so `item.save()` wrote the item under a new key and left the old item in the table. An `updatedAt` timestamp can still be an index key, and a `createdAt` timestamp can still be the `hashKey` or `rangeKey`. To keep a version per save, use your own sort key attribute and set it on each save
- A nested Schema with `saveUnknown: false` no longer allows every unknown property of its attribute. Before, it did the same as `saveUnknown: true`. Unknown properties that such an attribute stored with an earlier version are no longer returned by `Model.get`, `query` and `scan`, and saving an item read back removes them from DynamoDB. To keep them, set the nested Schema's `saveUnknown` to `true` or to a list of the properties to keep
- `item.save` no longer adds an object holding only a nested Schema's timestamps (`"address": {"createdAt": ..., "updatedAt": ...}`) to an item that doesn't have that attribute. A nested Schema's timestamps are now set only when the item has an object for it. Before, an item saved without `address` was stored with an `address` map of just the timestamps, and the save failed if the nested Schema had a `required` property
- A nested Schema's `get`, `set` and `validate` settings are now passed the object of its attribute (each element of a list), and `get` and `set` replace that object with what they return. They run before the schema's own functions, and aren't run when the item has no object for that attribute. Before, they were passed the whole item, and when the schema also had the same setting, every save or read threw `schemaValidator is not a function` or `schemaModifier is not a function`. A nested Schema's function that reads other attributes of the item should move to the schema's own settings
- `Model.update` and `Model.transaction.update` now call the schema's `set` setting once per update with the key and the attributes the update sets, and write what it returns. Before, it was called once for each attribute with only that attribute, so a function that read the key or another attribute got it missing, and an attribute it added was never written. Now an attribute it adds is set, an attribute it leaves out isn't written, and changing a key attribute throws `InvalidParameter`. It gets the key as the update was given it, and a key attribute it returns must be the one it makes from the key alone (the key `Model.get` uses), so a `set` that adds a prefix to the key works. The schema's `validate` gets what `set` returns. An update that only uses `$ADD`, `$REMOVE` or `$DELETE` doesn't call it
- A request DynamoDB always rejects for a missing or empty value now throws an `InvalidParameter` error before it is sent, instead of being sent and failing with DynamoDB's `ValidationException`. Code that catches the `ValidationException` for these cases gets the `InvalidParameter` error instead:
  - a condition value that is `undefined`, in `query`, `scan` and every write condition (`eq(undefined)`, `{"name": undefined}`, an `undefined` item of `in` or `between`, `between` with one value, or a raw condition placeholder without a value). Before, the chained form logged `Dynamoose Warning: Passing undefined into a condition ... is not supported` and sent the request; the warning is gone
  - a query key condition (on a hash or range key attribute of the table or of the index the query uses, including each attribute of a multi-attribute index key) whose value is `null`, an empty string or an empty binary value
  - a key that has no hashKey or rangeKey value, or a `null`, empty string or empty binary one, in `Model.get`, `Model.delete`, `Model.update`, `Model.batchGet`, `Model.batchDelete` and the `Model.transaction` methods. `Model.get(null)` threw `TypeError: Cannot convert undefined or null to object`
  - an item saved without a key attribute of the table, or with an empty string or binary value for a key attribute of the table or of an index, in `Model.create`, `item.save`, `Model.batchPut` and `Model.transaction.create`, and an update that sets a key attribute of an index to an empty string or binary value
  - a `beginsWith` value that isn't a string or binary value (such as `null` or a number), which DynamoDB's `begins_with` doesn't accept

### Features

- Added a `createdAtOnUpdate` schema setting, `true` by default. Set to `false`, `Model.update` and `Model.transaction.update` write only the `updatedAt` timestamps and leave `createdAt` out of the update. A value that isn't a boolean throws an `InvalidParameter` error.
- `Model.batchGet` now sends more than 100 keys, and `Model.batchPut` and `Model.batchDelete` more than 25 items, as several DynamoDB requests one after another, and combine their results and unprocessed keys or items. Before, DynamoDB rejected such a batch with `ValidationException: Too many items requested`. A batch sent as more than one request throws an `InvalidParameter` error, before sending any of it, when two of its keys or items have the same key, as DynamoDB does for a single request
- Added a `retryUnprocessed` setting to `Model.batchGet`, `Model.batchPut` and `Model.batchDelete`. With `{"attempts": n}`, Dynamoose sends the keys or items DynamoDB returns as unprocessed again, up to `n` times with exponential backoff and full jitter (`delay`, default 100 ms), and returns only what is still unprocessed after that. Each wait is at most 20 seconds
- Added a `concurrency` setting to `Model.batchGet`, `Model.batchPut` and `Model.batchDelete`, which sends that many of a large batch's DynamoDB requests at a time (default 1)
- Added support for enabling and configuring DynamoDB Streams through Table options
- Added `clientRequestToken` and `retry` settings to `dynamoose.transaction`. `clientRequestToken` is sent as the `ClientRequestToken` of a write transaction, so DynamoDB applies the same request only once for 10 minutes (a transaction rebuilt for a model with `timestamps` is a different request, and fails with `IdempotentParameterMismatchException` if it reuses the token). `retry: {attempts, delay}` sends the transaction again, with exponential backoff and full jitter, when DynamoDB cancels it for a `TransactionConflict` or reports `TransactionInProgressException`; any other error is thrown at once. Every attempt sends the same `ClientRequestToken` (the one passed in, or one Dynamoose makes for the call and replaces after a cancellation), so a transaction still in progress is never applied twice, and each wait is at most 20 seconds
- Added a `merge` setting to `Model.update`. Passing `{"merge": true}` updates a nested object in place by writing each provided property to its own document path (`SET attr.sub = :v`), matching how a nested attribute update is expressed against DynamoDB directly, instead of replacing the whole attribute as a map. The default behavior is unchanged
- `condition.not()` now works with `in`, `between` and `beginsWith`, sent as `NOT (a IN (...))`, `NOT (a BETWEEN x AND y)` and `NOT begins_with (a, x)`. Before, these threw `can not follow not()`
- Added support for enabling table deletion protection through the `deletionProtection` Table option. It is applied on create, and on update it can only be turned on; turning it back off requires `update` to explicitly include `deletionProtection`
- Added `Model.itemFromDynamo(attributes)`, which converts an item in DynamoDB's format (such as a DynamoDB Stream `NewImage` or an AWS SDK `Item`) into an item of the model, as `Model.get` would return it, with custom types such as `Date` converted by their `storage` setting. It takes the image typed as `@types/aws-lambda` types it, and decodes the base64 binary values a Lambda event has
- Added support for enabling point-in-time recovery through the `pointInTimeRecovery` Table option, including configuring the recovery window with `pointInTimeRecovery.recoveryPeriodInDays`. As with deletion protection, `update: true` can only turn recovery on; turning it back off requires `update` to explicitly include `pointInTimeRecovery`
- Added a `returnValuesOnConditionCheckFailure` setting to `Model.update`, `Model.create`, `item.save` and `Model.delete`, and so to their `Model.transaction` requests. With `ALL_OLD`, a failed condition (or an existing item for `create`) throws `ConditionalCheckFailedException` with a `conditionCheckFailureItem` property holding the stored item as `Model.get` would return it, so a caller can retry without reading the item again
- Added a `returnItems` setting to `dynamoose.transaction`, so a write transaction resolves with the written items in the same order as the request: a `create` gives the stored item built from the request, an `update` gives the stored item read back in one `transactGetItems` call, and a `delete` or `condition` gives `undefined`. Each item uses the model that built its request and looks as `Model.get` would return it. If the write succeeds but the items can't be returned, the promise rejects with a `TransactionReadError` whose `committed` property is `true`
- Added a `returnValuesOnConditionCheckFailure` setting to `dynamoose.transaction`. Set to `ALL_OLD`, it is passed as `ReturnValuesOnConditionCheckFailure` on every write request that has a condition, and when a condition fails, the `TransactionCanceledException` gets a `conditionCheckFailureItems` property: one entry per request, holding the stored item (as `Model.get` would return it) of each request whose condition failed on an existing item
- `$ADD` on a list attribute in `Model.update` and `Model.transaction.update` now creates the list when the item doesn't have it yet, or when the update creates the item. Before, such an update failed with `ValidationException: The provided expression refers to an attribute that does not exist in the item`. A list is now appended with `SET #a0 = list_append(if_not_exists(#a0, :v1), :v0)`, so a missing list starts out empty. When an update appends to a list, the request has one more value, an empty list (`{"L": []}`) numbered after the update's other values

### Performance

- Improved performance of converting items returned from `scan` and `query` (~2x faster on large result sets). `Schema` now memoizes `attributes`, `getAttributeValue`, `getAttributeType`, and `getAttributeTypeDetails` per schema, and object flattening no longer re-walks each nested value's subtree to detect circular references
- Improved performance of `Model.update` on items with many nested attributes when the schema has nested `required` attributes (~460x faster for a 2,000 element list: 24.6 s to 54 ms). The update flattened the whole item once for every attribute it checked; it now flattens it once
- Improved performance of items containing a long list of attributes with multiple possible types (~4x faster for a 800 element list). Building the type paths for such an item no longer copies the accumulated result once per element

### Bug Fixes

- Fixed reading an item dropping an attribute with several types that has an `alias` (or `map`/`aliases`) on its types. The attribute was renamed to a key made of its types' empty `defaultAlias` values (`","`) instead of to its alias. Saving through an alias that is a list (`"aliases": ["p", "q"]`) on such an attribute now works too
- Fixed a schema throwing `Only defaultMap or defaultAlias can be specified per attribute.` for an attribute with several types that has the same `defaultMap` or `defaultAlias` on each type. Different values on different types, or both settings, still throw
- Fixed saving an item whose attribute with several types gets its `default` value: the attribute's `set`, `validate` and `enum` settings were looked up for all its types at once, so the save failed with a `ValidationError` or `modifierFunction is not a function`. The default value now picks the type, as a value passed in does
- Fixed an attribute whose types are given as its `type` setting (`{"type": [{"type": Object, "schema": {...}}, ...]}`) losing every nested attribute when saved and read. It now works as the same types given as a list
- Fixed saving and reading an item dropping the properties of the maps in a list for an attribute with several types when an earlier type also has something at the list's element path, such as `[{"type": Set, "schema": [String]}, {"type": Array, "schema": [{"type": Object, "schema": {"name": String}}]}]`. `[{"name": "Bob"}]` was saved and read as `[{}]`. The schema now looks up a nested attribute in the type that has the whole path, and lists the nested attributes of each of an attribute's types within that type
- Fixed `Model.update` and `Model.transaction.update` calling the schema's `validate` setting once for each attribute the update sets, each time with only that attribute, so a function that checked the key (such as `item.id`) or two attributes together rejected every update. It is now called once per update with the key and the values the update sets, including forced defaults and timestamps, and the schema matching the update's values is used. When the schema also has a `set`, `validate` is given what `set` returns. An update that only uses `$ADD`, `$REMOVE` or `$DELETE` still doesn't call it
- Fixed a condition (`query`, `scan`, `filter` and write conditions) on an attribute with a `set` function throwing a `TypeError` such as `value.toLowerCase is not a function`, because the attribute's name was looked up by calling its `set` function with `true`. With a schema-level `set` that adds attributes, the condition was also sent for the wrong attribute or threw `Error retrieving requestObject from Condition`. The name is now found without calling `set` functions, and the value is the one for the condition's attribute
- Fixed `Model.batchPut` leaving out of `unprocessedItems` an item DynamoDB didn't write when the item has a `Date` attribute or a `Set` given as an array, so the write was lost without an error. Unprocessed items are now matched to the items sent by their key. With a hash key that comes from a `default`, each unprocessed item was also listed once for every item that looked the same.
- Fixed `Model.get`, `Model.delete`, `Model.batchGet` and `Model.update` putting the attributes a schema's `set` setting adds into the request's `Key` when the key was passed as a value (`Model.get(1)`), so DynamoDB rejected the request with `The provided key element does not match the schema`. Only the hash key is sent now, as for a key passed as an object
- Fixed `item.save` not setting the timestamps of a nested Schema when the item used the attribute's mapped name (`map` or `alias`). For an attribute holding a nested Schema it threw `Cannot map attribute addr to address because both are defined`, including when saving an item read with `Model.get`, and for a list of nested Schemas the timestamps were left out
- Fixed a nested Schema whose `timestamps` names are a list (`{"createdAt": ["created", "added"]}`), `null` or a definition with settings, or a Schema nested in another nested Schema where every level has `timestamps`, making every `item.save`, `Model.update` and `Model.transaction.update` throw `Invalid Attribute: 0` or `Invalid Attribute: address.null`
- Fixed the `timestamps` and `saveUnknown` settings of a nested Schema used as one of an attribute's types (`{"data": [{"type": Object, "schema": addressSchema}, String]}`) not applying, and `item.save` throwing `Cannot read properties of undefined (reading 'schema')` or `Cannot create property 'createdAt' on string` for such an attribute
- Fixed a nested Schema's `indexes` setting being added to the schema it's used in, and to the other nested Schemas used next to it, so a model built from that nested Schema created indexes of another Schema
- Fixed the callback of `Model.get`, `Model.update`, `Model.delete`, `Model.batchGet`, `Model.batchPut`, `Model.batchDelete`, `query.exec`, `scan.exec`, `item.populate`, `dynamoose.transaction`, `table.create`, `table.initialize`, a custom method and `item.save` with `return: "request"` being called a second time, with its own error, when it threw. The error is now left unhandled, as `item.save` already did
- Fixed `new dynamoose.Schema` modifying the schema definition and settings objects passed to it, including objects without a prototype (`Object.create(null)`) and objects from another realm (`vm`). `timestamps: true` was replaced with an object that a nested Schema's timestamp names were added to, the timestamp attributes were added to the definition, and a nested Schema inside an object or list attribute was replaced with a plain object. Passing the same settings object to two schemas with nested Schemas that have `timestamps` threw `Attributes must not contain dots.`, and passing the same definition to two schemas with `timestamps` threw `Timestamp attributes must not be defined in schema.`
- Fixed the `timestamps` and `saveUnknown` settings of a nested Schema inside an object attribute (`{"type": Object, "schema": {"address": addressSchema}}` or `{"type": Object, "schema": addressSchema}`) or a list (`{"type": Array, "schema": [addressSchema]}`) applying to its path in the schema definition (`info.schema.address`) instead of in the item (`info.address`). Unknown properties the nested Schema allowed were left out when saving and reading the item, its timestamps were never set, and with `timestamps` on the parent schema too, `item.save` threw `Cannot read properties of undefined (reading 'schema')`. When the parent schema has `timestamps` too, `item.save` now sets the nested timestamps, on every element of a list, as it already did for a nested Schema set directly as an attribute. `createdAt` is set only when the whole item is new, so an element added to a list of a stored item gets `updatedAt` but no `createdAt`
- Fixed a schema with `saveUnknown: true` throwing `key.split is not a function` when saving or reading an item with an unknown property if a nested Schema had a `saveUnknown` setting. The parent's `saveUnknown: true` now allows every unknown property, the nested ones included
- Fixed `Model.update` and `Model.transaction.update` on a model with several schemas always following the first schema's rules. An attribute only a later schema defines was skipped when set to `undefined`, so the update was sent empty and DynamoDB rejected it, and its `required` and `default` settings were ignored. An update now follows the schema that defines the most of the attributes it names (on a tie, the one whose types match the values it sets, then the first), including that schema's `forceDefault`, timestamps and `Combine` attributes, and each attribute's `enum`, `validate` and `set` settings.
- Fixed `Model.update` and `Model.transaction.update` ignoring an attribute named by its `alias`, `aliases` or `map` name in the update object, which left it out of the update. The key in a single object (`Model.update({"email": "a@b.c", "name": "Bob"})`) can still be named by its alias. An update that names one attribute twice, such as an attribute and its alias, now throws an `InvalidParameter` error instead of writing the last value
- Fixed a model with several schemas matching an item to the wrong schema when the item named a later schema's attribute by its `alias`, `aliases` or `map` name. Saving it (`Model.create`, `item.save`, `Model.batchPut`, `Model.transaction.create`) left out that schema's attributes, so `{"id": 1, "b": "x", "dee": "y"}` was stored as `{"id": 1}`, and reading it back (`Model.get`, `query`, `scan`, `Model.batchGet`, transaction get, the item `Model.update` resolves with, `Model.itemFromDynamo`) left out the aliased attribute. An attribute named by its alias now counts as that attribute when an item is matched to a schema
- Fixed `item.populate()` and `populate()` on `scan` and `query` results not populating an attribute with several types that holds a Set of models (`{"type": [Set, String], "schema": [[User]]}`). The Set is now populated as a list of the items, and a value of the attribute's other types is left as it is
- Fixed `item.populate()` and `populate()` on `scan` and `query` results throwing `TypeError: Cannot read properties of undefined (reading 'getInternalProperties')` when a referenced item doesn't exist. The reference keeps its key, in its place in a list or Set of references, so saving the item after `populate` keeps it
- Fixed `Model.create` and `item.save` resolving with an item that named its attributes by their names instead of their `alias`, `aliases` or `map` names, unlike `Model.get`. The item they resolve with now uses the same names `Model.get` returns. The request sent and the item `save` was called on are unchanged
- `@kennethwkz/dynamoose` now depends on `@kennethwkz/js-object-utilities` (installed under the name `js-object-utilities`), a fork whose `entries` treats binary values as leaves and detects cycles in linear time. This fixes `Model.get`, `query` and `scan` throwing `RangeError: Maximum call stack size exceeded` for an item with a large binary attribute (dynamoose/dynamoose#1608). Paths through `__proto__` are ignored by `delete`, as in js-object-utilities 2.2.2
- Fixed `Model.create` and `item.save` resolving with an item that left out the attributes the schema's `saveUnknown` setting allows (for example everything under `order.**`), and `item.save` removing them from the item it was called on. The stored item was correct, and `Model.get` returned them; the returned item now matches it
- Fixed `Model.update` failing with `ValidationException: Two document paths overlap` when the update sets or removes a timestamp attribute itself (for example `{"updatedAt": date}` or `{"$REMOVE": ["updatedAt"]}`). Dynamoose no longer adds its own value for a timestamp attribute that the update already names
- Fixed `Model.update` and `Model.transaction.update` writing the default of the table's hash or range key when the attribute has `forceDefault: true`, which DynamoDB rejects ("Cannot update attribute ... This attribute is part of the key"). The key keeps the value it has. A forced default on an index key is still written
- Fixed `deep_copy` dropping sibling properties that share the same object reference (e.g. a single `Date` used for both `createdAt` and `updatedAt`, or a single address used for both `billingAddress` and `shippingAddress`). Circular reference detection now tracks only the current ancestor path rather than every object ever visited, which also removes an infinite-recursion risk on self-referencing arrays and a shared-reference leak on class instances containing circular properties
- Fixed `query.consistent()`, `scan.consistent()`, `query.count()` and `scan.count()` ignoring their argument and flipping the setting on every call, so `consistent(false)` sent `ConsistentRead: true` and calling a method twice turned the setting off. They now take an optional boolean, and calling them without one turns the setting on
- Fixed `Model.update` corrupting arrays, Sets, and Buffers nested inside a map attribute. These values were traversed as if they were nested maps, which produced document paths keyed by array indices or byte offsets, and silently dropped Sets from the update entirely
- Fixed `Item.attributesWithSchema` throwing `node.forEach is not a function` when an object was supplied for an attribute the schema defines as an array
- Fixed `Model.update` rejecting partially specified nested attributes at the type level. Update bodies are now typed as `DeepPartial<T>`
- Fixed the TypeScript type of `table.create({"return": "request"})`, which resolved to `Promise<void>` instead of `Promise<CreateTableInput>` because a general overload came first, and `table.create({})`, which matched no overload because `return` was a required setting
- Fixed the `save` callback being invoked a second time when the supplied callback itself threw an error
- Fixed the `expires` TTL attribute being silently dropped from every model registered against a table after the first. A model attaching to an already-constructed table did not receive the TTL attribute injection the `Table` constructor performs, so its writes stored no TTL attribute at all while DynamoDB continued to report `TimeToLiveStatus: ENABLED`. Affected every table shared by two or more distinct `Schema` objects, across `create`, `transaction.create`, and `update`
- Fixed a global secondary index whose name is unchanged but whose key schema or projection changed being deleted without being recreated. Such an index was only restored on a later `initialize`, leaving the table without it in between. The delete and the recreate are now emitted in the same reconciliation pass, in that order
- Fixed `queriedCount` always being `undefined` on `Model.query` results. The count of items DynamoDB read before applying filters was looked up on the response as `QueriedCount`, a property the DynamoDB API never returns; the `Query` operation reports it as `ScannedCount`, the same as `Scan`. This affected `query.exec`, `query.all`, and `query.count`, in both the array and `count()` response shapes
- Fixed `dynamoose.transaction` get results skipping schema `get` modifiers. Items returned from a `transactGetItems` transaction now run attribute `get` functions the same as `Model.get`, `Model.batchGet`, `Model.query`, and `Model.scan`
- Fixed `Model.update` resolving with an item that skipped schema `get` modifiers. The item returned from the `updateItem` response now runs attribute `get` functions the same as `Model.get`, `Model.batchGet`, `Model.query`, and `Model.scan`
- Fixed `Model.batchGet`, `Model.update` and `dynamoose.transaction` get results not applying the schema `map`/`alias` settings. Items returned from these methods now use the mapped attribute names, the same as `Model.get`, `Model.query`, and `Model.scan`
- Fixed mapped attributes being dropped from items returned by `Model.get`, `Model.batchGet`, `Model.update` and `dynamoose.transaction` get on a model with multiple schemas when the item matched a schema other than the first one. The mapping re-selected the schema from the already-renamed item and could pick the first schema, which skipped the renamed attributes
- Fixed a mapped (`map`/`alias`) attribute being dropped from a returned item when its value was falsy (`0`, `false` or an empty string)
- Fixed `Model.batchGet` throwing `TypeError: Cannot read properties of undefined` when DynamoDB returned an expired item on a table with `expires.items.returnExpired` set to `false`. Expired items are now left out of the result, the same as `Model.query` and `Model.scan`
- Fixed `Model.batchGet` silently leaving out items whose key attribute has a `get` function. Requested keys were matched against the item after its `get` functions ran, so a key stored as `user#1` and returned as `1` never matched; keys are now matched against the item as DynamoDB returned it
- Fixed `Model.batchGet` silently leaving out items, and unprocessed keys, whose key is a `Buffer`. Key values were compared with `===`, which is never true for two `Buffer` instances; they are now compared by content
- Fixed `Date` and `Buffer` key values in `Model.get`, `Model.batchGet`, `Model.delete`, `Model.batchDelete`, `Model.update` and the `Model.transaction` methods. A `Date` or `Buffer` passed as the hash key sent an empty `Key` to DynamoDB, and a `Date` inside a key object threw `Unsupported type passed`. `Date` key values are now converted using the attribute's `storage` setting before the attribute's `set` function runs, the same as when saving an item (previously a key's `set` function received the `Date` itself), and the key types accept `Date` and `Buffer` values. `Model.batchDelete` also now reports unprocessed items whose key is a `Buffer`; key values were compared with `===`, which is never true for two `Buffer` instances
- Fixed a serializer `exclude` path into a nested object or list (such as `"address.city"` or `"lines.0.cost"`) deleting the value from the item itself, so a later `save` could write the change to DynamoDB. The plain objects and lists along each excluded path are now copied before deleting, so the item is left as it was and the serialized output is unchanged. An `exclude` path with a `__proto__`, `constructor` or `prototype` part is now ignored, as js-object-utilities 2.2.2 ignores it, instead of deleting from a built-in prototype such as `Object.prototype`
- Fixed `condition.not()` before `condition.parenthesis()` or `condition.group()` being silently ignored, so the group was applied un-negated and returned the opposite items. It is now sent as `NOT (...)`
- Fixed a `Date` value in a condition throwing `Unsupported type passed` in `query`, `scan` and conditional writes. A `Date` is now sent the way its attribute stores it (milliseconds, seconds or ISO string), including in `between` and `in` and on nested attributes (`meta.when`), and a `Date` for an attribute that isn't a `Date` throws a clear `InvalidParameter` error
- Fixed `dynamoose.transaction` rejecting with `No value defined: {}` when a `Get` asked for an item that does not exist. The result now has `undefined` at that position, in the same order as the request
- Fixed a raw condition object being silently ignored when its expression property didn't match the request. A `FilterExpression` raw condition passed to `Model.update`, `Model.delete`, `Item.save` or a transaction was dropped, so the write ran without its condition; a `ConditionExpression` raw condition passed to `query` or `scan` was dropped, so no filter was applied. Either property is now used for both, and any other property (such as `ComparisonExpression`, which the documentation previously named) throws an `InvalidParameter` error
- Fixed `Model.update` adding its update expression, names and values to the raw condition object passed in, which made a reused raw condition throw or be ignored on the next request
- Fixed a raw condition object without `ExpressionAttributeValues` (for an expression that uses no values, such as `attribute_exists(#id)`) throwing `The type: #id is invalid`. It is now used as a raw condition, and the request leaves out `ExpressionAttributeValues` unless something else in the request adds values
- Fixed `Model.query` with a raw condition object throwing `Index can't be found for query.`. Dynamoose now splits the raw expression at its top-level `AND`s, picks the index from the parts that are key conditions, and sends those as the `KeyConditionExpression`, leaving the rest in the `FilterExpression`. A second condition on the same key attribute throws an `InvalidParameter` error, because DynamoDB rejects a key attribute in the `FilterExpression`
- Fixed `Model.update` replacing a raw condition's names and values when they used the same placeholders as the update (`#a0`, `:v0`), which made the condition silently check a different attribute or value. The update's placeholders now start after the raw condition's
- Fixed a raw condition object with an empty `ExpressionAttributeNames` (an expression that names its attributes directly, such as `id = :id`) or an empty `ExpressionAttributeValues` sending that empty map, which DynamoDB rejects. An empty map is now left out
- Fixed a raw condition object passed to `condition.parenthesis()` or `condition.group()` being dropped, which made `Model.query` throw `TypeError: Cannot read properties of undefined (reading '0')` and a scan or conditional write run without it. It is now sent in parentheses with its own names and values, and two raw conditions that use one placeholder for different names or values throw an `InvalidParameter` error
- Fixed the `Condition` documentation naming `ComparisonExpression` instead of `ConditionExpression` for raw condition objects, and a raw example using a number instead of a string for an `N` value
- Fixed `Model.update` and `Model.transaction.update` throwing `TypeMismatch` (`Expected friends.0 to be of type string, instead found type undefined.`) for a list attribute set to `undefined`. The value was wrapped in a list before the `undefined` check, so it became `[undefined]`. A list attribute set to `undefined` is now handled as any other attribute is: removed (`REMOVE`), set back to its `default`, or rejected with a `ValidationError` when `required`. A single value for a list attribute (`{"$ADD": {"friends": "Tim"}}`) is still wrapped in a list
- Fixed `Model.update` and `Model.transaction.update` with `{"merge": true}` sending `SET #a0.#a1 = :v2` without a value for `:v2` when a nested property was `undefined` or `dynamoose.type.UNDEFINED`, a request DynamoDB rejects. The nested property's document path is now removed (`REMOVE #a0.#a1`), and a nested `required` property throws a `ValidationError`
- Fixed `Model.update` and `Model.transaction.update` throwing `You must update all or none of the combine attributes` when the update doesn't change any of the attributes a `Combine` attribute is made from. As documented, such an update now leaves the combine attribute as it is
- Fixed `Model.update` and `Model.transaction.update` not writing a `Combine` attribute when the model also has a `forceDefault` attribute. Both were given the same placeholder (e.g. `#a2`), so the request set the default value twice and left the combine attribute out. With `merge: true`, the combine attribute could also take the placeholder of a nested property's value, which wrote the combine value into the nested property
- Fixed `Model.update` and `Model.transaction.update` with `{"merge": true}` treating a nested property as the top-level attribute with the same name. A nested property named like a combined attribute counted as that attribute, so an update that changed only the nested property threw `You must update all or none of the combine attributes`, and one that also set the other combined attributes wrote a combine value without the stored attribute. A `forceDefault` attribute was left out when a nested property had its name
- Fixed `Model.update`, `Model.batchPut`, `Model.create` and `item.save` never calling the callback when `return: "request"` is set and building the request fails (for example, a `set` function throws). The callback now receives the error, instead of the error becoming an unhandled promise rejection
- Fixed `Model.update` and `Model.transaction.update` replacing an attribute that is a nested Schema with `timestamps` with just its timestamps (`SET address = {"createdAt": ...}`) when the parent schema also has `timestamps`, which deleted every other property of that attribute. Updates now set only the top-level timestamps. This also fixes such an update throwing `Cannot read properties of undefined (reading 'schema')` for a list of nested Schemas with `timestamps`
- Fixed `Model.update` and `Model.transaction.update` counting a combined attribute changed with `$ADD` or `$DELETE` as set when the update also set an attribute whose placeholder starts with its placeholder (`#a1` and `#a10`). The combine value was built from the amount added instead of throwing `You must update all or none of the combine attributes`
- Fixed a condition object with an `undefined` or `null` value (`Model.query({"id": undefined})`, `Model.scan({"name": null})`) throwing `TypeError: Cannot read properties of undefined` or `Cannot convert undefined or null to object` when it was built, and `{"name": {"eq": null}}` comparing the attribute with the map `{"eq": null}`. A `null` value is now compared with `NULL`, as `eq(null)` does
- Fixed a condition value that is an empty list, map or binary value (`filter("tags").eq([])`) being left out of the request, which DynamoDB rejected. Only an empty `ExpressionAttributeNames` or `ExpressionAttributeValues` is left out now
- Fixed `item.save`, `Model.batchPut` and `Model.update` with `{"return": "request"}` and a callback never calling the callback when building the request failed
- Fixed `condition.ne()`, `query.ne()` and `scan.ne()` missing from the TypeScript types, so TypeScript code couldn't call them although they work at runtime. A comparison method that isn't declared in the types now fails to compile, and `condition.ne()` is documented
- Fixed `Model.update` and `Model.transaction.update` writing a nested `forceDefault` attribute to a new top-level attribute named after its path (for example `"config.timeout": 5`). Without `merge`, every update wrote it; with `{"merge": true}`, every update that didn't write its parent, unless the update merged a nested property named like the parent. A nested forced default is now applied only when the update writes its parent
- Fixed `Model.batchGet` with an `attributes` setting that leaves out the table's hash or range key returning no items. DynamoDB returned the items, but without their key attributes they couldn't be matched to the keys, so they were dropped. The key attributes are now requested too, and left out of the returned items unless `attributes` lists them, as `Model.get` does
- Fixed `Model.itemFromDynamo` throwing `TypeError: Cannot convert undefined or null to object` for an item with a null value where an attribute value belongs, such as `{"a": {"M": null}}` or `{"a": {"L": [null]}}`. It now throws the `InvalidParameter` error it throws for any other item that isn't in DynamoDB's format
- Fixed `item.toDynamo()` leaving out every attribute the schema doesn't name, even when the schema's `saveUnknown` setting allows it, so its result differed from what `item.save` stores (#1679). It now applies the schema's `saveUnknown` setting, unless `saveUnknown: false` is passed in its settings
- Fixed `item.save`, `Model.create`, `Model.batchPut` and `Model.update` with a list of two or more models (`{"type": Array, "schema": [User]}`) or of `dynamoose.type.ANY` objects. Only the first element of such a list was type checked, so the properties of every other element were removed as properties the schema doesn't name: a list of models threw `Unsupported type passed: [object Object]` (as did saving an item after `populate` filled such a list), and a list of `dynamoose.type.ANY` objects was saved with every element after the first one empty

### Other

- Built every stored condition comparison with one function, so each holds exactly one attribute, which the code reading them relies on. This replaces a TODO about comparisons that could hold several attributes; no behavior changes
- Fixed intermittent CI failures in timing-based tests. Timestamp tests now check that the value falls between the time before and after the call instead of within 10ms of a single reading, and the `Scan`/`Query` `all` delay and `Table` TTL wait tests allow for timers firing about 1ms early
- Documented what `Model.update` does with an attribute set to `undefined`: it is set back to its `default`, removed, rejected when `required`, or skipped when it isn't in the schema
- Fixed the `Table` constructor's `models` parameter type, which accepted any `Model`. It is now typed as the models `dynamoose.model` returns, so passing a value the constructor rejects at runtime (such as `User.Model`) is a type error instead of a runtime error
